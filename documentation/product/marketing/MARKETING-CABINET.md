## Иерархия данных

1. **Компании** (`/api/v1/companies`) — арендатор; владелец и при необходимости представитель (`representative_user_id`).
2. **Проекты** (`/api/v1/projects`) — привязка к компании; руководитель проекта = `created_by`.
3. Сущности кабинета (JTBD, VP, и т.д.) запрашиваются с **`project_id`** (и при необходимости `company_id`) через префикс маркетингового API.

## Данные, RAG и автозаполнение (как устроено сейчас)

**Термины в интерфейсе:** для маркетолога в подписях и турах используются нейтральные формулировки про **поиск по материалам проекта**, **индекс** и **источники для поиска**; аббревиатура **RAG** и внутренние имена (`imc_rag_*`, UGS и т.п.) остаются в операторской и технической документации ниже и в коде.

- **ИМК (исследования):** основные типы с префиксом **`imc_rag_*`** исполняются провайдером **`imc_rag_research_provider`** (контекст Postgres + RAG по документам vault, **без веб-поиска**). **MISO не используется** для этих типов (набор активных `imc_rag_*` расширяется SQL-миграциями; см. список в подразделе ниже). Подробности, список `type_key` и диаграмма — [IMC-MISO-ARCHITECTURE.md](IMC-MISO-ARCHITECTURE.md). При расхождении с кодом ориентир — `IMC-MISO-ARCHITECTURE.md` и миграция `*_imc_rag_research_provider_and_types.sql` (исторические archive/project-pack snapshots soft-retired).
- **Контекст для AI** в маркетинговом кабинете двухслойный: (1) агрегат из **PostgreSQL** (`build_project_context` — карточка проекта, компания, ключевые поля сущностей); (2) **семантические фрагменты** из загруженных документов проекта в **Qdrant**, коллекция **`marketing_project_rag`** (чанки `unified_content.extracted_text`, фильтр по `marketing_project_id`). Второй слой **не заменяет** первый и **не включает** по умолчанию чаты, исследования и прочие сущности, если они не попали в текст извлечённых файлов.
- **Поиск RAG**: эмбеддинг запроса → `query_points` с фильтром по проекту → объединение с текстом Postgres через `merge_project_context_text_with_rag`. Доступ к проекту проверяется тем же `get_accessible_project`, что и в API кабинета.
- **Индексация в Qdrant** запускается после обработки контента в очереди и при обновлении `extracted_text`; при удалении контента точки удаляются. Подробности, лимиты чанков, MIME, потребители (AI Studio, чат, JTBD, SWOT, исследования, IMC, autofill) — в **[MARKETING-PROJECT-RAG.md](MARKETING-PROJECT-RAG.md)**.

### ИМК: типы исследований и UI

- **Список типов:** `GET /api/v1/marketing-cabinet/imc/types` — из `generation_types` для кабинета. **Актуальный кураторский набор (15 типов, промпты v2, без orchestrate):** [IMC-RESEARCH-TYPES-PLAYBOOK.md](IMC-RESEARCH-TYPES-PLAYBOOK.md), миграция `applied/20260621_imc_rag_research_types_curated.sql`. Тип **`imc_rag_deep_market_showcase`** снят с выдачи; наследник — **`imc_rag_cabinet_analysis`**. Шесть прежних `imc_*` (ландшафт, аудитория, GTM и т.д.) — неактивны. **`imc_cabinet_filler`** — отдельный тип с JSON-ответом. **`marketing_research_creator`** в список кабинета **не** попадает (MISO вне UI).
- **Целостность БД и провайдеров:** идемпотентная миграция `shared/api/migrations/applied/20260415_imc_generation_types_provider_repair.sql` выключает шесть legacy `imc_*`, выравнивает активные `imc_rag_*` на `imc_rag_research_provider` и чинит ошибочное сочетание «активен + `miso_provider` + ключ `imc_%`» (кроме `marketing_research_creator`). При старте API нарушение инварианта логируется как **ERROR**; при `ELITEEW_STRICT_IMC_GENERATION_TYPES=1` процесс падает на старте. Запуск ИМК с устаревшим `type_key` (например `imc_gtm_channels`) даёт **400** с телом `deprecated_imc_type` и полем `successor_type_key`. Для типов с **`imc_rag_project_only`** без контекста проекта после обогащения — **422**; при недоступности эмбеддингов/Qdrant в этом режиме — **503** (вместо тихого пустого контекста).
- **`rag_project_only`:** в ответе типа может быть флаг (поле вроде `rag_project_only` / согласованное имя в OpenAPI): при `true` пользователь может запускать исследование **без** обязательного файла/URL/брифа — оркестратор опирается на контекст проекта и RAG; в UI показывают подсказку про загрузку документов в vault для качества.
- **Код и схемы:** `shared/api/routers/marketing_cabinet/imc.py`, `api/schemas/imc.py`, `api/services/imc/imc_service.py`; фронт — facade `views/ImcResearchView.tsx` → `views/imcResearch/*` (`ImcResearchView` compose, `useImcResearchController`, list/run/detail/compare panels, helpers/types), hooks `useImcResearch.ts`, `imcClient.ts`. **История по проекту** видна всем с доступом к проекту (не только автору запуска); в ответах — кто запустил (`started_by_*`). **Удаление записи из истории** — только руководитель проекта (`projects.created_by`), `DELETE /api/v1/marketing-cabinet/imc/research/{id}`. Отмена и повтор запуска — автор запуска или руководитель. В UI списка: поиск/сортировка/«только активные», догрузка страницей; в карточке запуска: метаданные (UGS request id, снимок `imc_prompt_version`), подстановка параметров в форму нового запуска, выгрузка markdown/JSON результата.
- **Лимиты:** `POST .../imc/research/run` и `POST .../imc/research/{id}/rerun` проходят через тот же лимит AI маркетингового кабинета, что и чат/прочие маршруты (`check_marketing_cabinet_ai_rate_limit` в `rate_limit.py`): при превышении — **429** и заголовок `Retry-After`.
- **Префлайт vault/RAG:** `GET .../imc/project/{project_id}/rag-hints` — счётчики Qdrant по проекту и документов в Postgres с текстом; флаг `weak_coverage` для баннера в UI. Лимит размера промпта перед Llama: `IMC_RAG_MAX_PROMPT_CHARS` (шаги / single-shot) и отдельно **`IMC_RAG_MERGE_MAX_PROMPT_CHARS`** для финальной сборки оркестрации; плюс `IMC_RAG_LLAMA_NUM_CTX` в `options` у Llama. Логи: `[STEP] imc.rag_research.prompt_truncated`, `merge_prompt_truncated`.
- **Автозаполнение разделов** (`/marketing-cabinet/autofill/...`): режимы **preview** / **apply**; источник **файл проекта** (`content_id` + текст документа) или **только контекст проекта + RAG** (`/generate-from-project/async`); генерация через UGS **`document_structured_extract`** со stack2 **`format=json`** (без fallback на `text_chat`), учёт записей в `marketing_ai_runs`, rate limit и idempotency — детально в том же файле **MARKETING-PROJECT-RAG.md**, §5. SWOT/JTBD async — отдельные type_key **`marketing_swot_analysis`** / **`marketing_jtbd_extract`** (миграция `applied/20260620_marketing_structured_llm_generation_types.sql`).

### Evidence: брифы исследований (`research_projects`)

- **UI:** вкладка «Свидетельства» — `EvidenceView.tsx`; форма брифа, список, AI-синтез результата.
- **Типы:** `GET /api/v1/marketing-cabinet/researches/types` — каталог `api/services/marketing_cabinet/research_type_catalog.py` (**9 типов** в UI: рынок, клиенты, конкуренты, продукт, SWOT, JTBD, ценность, тренды, свой). Legacy enum PG (`business`, `porter`, `opportunity_analysis`, `risk_assessment`) скрыты; при создании/обновлении нормализуются в активные ключи.
- **Синтез:** `POST .../researches/{id}/run` (sync) и **`POST .../researches/{id}/run/async`** (202 + poll `marketing_ai_runs`). Промпт только по контексту проекта + RAG, структура ответа по типу; запрет веб-поиска и «воды» без цитат из материалов.
- **Async-порядок:** `processing` на `research_projects` выставляется **после** регистрации `marketing_ai_runs` (не до UGS), чтобы не оставлять «висящие» карточки без фоновой задачи.
- **Reconcile зависших:** `GET .../researches?project_id=…` вызывает `research_run_reconciliation.py` — сироты `processing` без ai_run → `failed` после grace **`MARKETING_RESEARCH_ORPHAN_GRACE_MINUTES`** (default 2); активные ai_run → poll UGS через `ai_run_reconciliation`; в ответе у processing — **`active_ai_run_id`** для resume poll в UI после F5.
- **Миграция данных:** `applied/20260621_02_evidence_research_types_curated.sql`.

- **AMKA** (только **маркетинговые прогоны** в кабинете; **не** EWA / **EwaApp** — [AMKA-CONTOURS.md](../amka-seed-album/AMKA-CONTOURS.md)): staged-аудит с lifecycle store (`marketing_amka_runs`, `marketing_amka_run_steps`). UI: `src/features/amka/` (`MarketingCabinetAmkaView`). HTTP: `/api/v1/marketing-cabinet/amka/*`. При mutation write-back связи сегментов резолвятся через БД проекта (titles → UUID), см. [AMKA-REFERENCE.md](AMKA-REFERENCE.md) §9.1. Markdown-экспорт: `GET /api/v1/marketing-cabinet/amka/runs/{run_id}/export.md`. **Ассистент:** [AMKA-REFERENCE.md](AMKA-REFERENCE.md). Техмодули: [amka/README.md](amka/README.md). Workflow: [AMKA-AUDIT-WORKFLOW.md](AMKA-AUDIT-WORKFLOW.md). Фаза аудита: [amka/modules/module-amka-phase-audit.md](amka/modules/module-amka-phase-audit.md). Seed/видение драйверов (не runtime): [../amka-seed-album/README.md](../amka-seed-album/README.md).

### Финализация долгих AI-запусков (`marketing_ai_runs`, бэкенд)

- Асинхронные сценарии с **UGS** (JTBD extract, SWOT generate, **Evidence research_run**, превью autofill и т.п.) записывают старт в **`marketing_ai_runs`**; доведение до статуса «готово» / «ошибка» и запись результатов в доменные таблицы выполняется **централизованно** модулем **`api/routers/marketing_cabinet/ai_run_reconciliation.py`** (poll статуса UGS, обновление строки run, согласованные финализаторы по `result_type`). Для **`research_projects`** дополнительно **`research_run_reconciliation.py`** на list: сброс сирот и `active_ai_run_id` для UI. При добавлении новых async-потоков кабинета не дублировать ожидание UGS в роутерах — расширять reconciliation и общие хелперы там же.

### Обзор проекта: карточки и дашборд

Канонические определения метрик быстрой сводки, формула **готовности** и различие «индекс vs счётчики» — **[OVERVIEW-SUMMARY-SPEC.md](OVERVIEW-SUMMARY-SPEC.md)**.

**Статус интерактивного дашборда (MVP+, 2026-04-18):** контур считается готовым к эксплуатации после прогона [DASHBOARD-REGRESSION-CHECKLIST.md](DASHBOARD-REGRESSION-CHECKLIST.md), зелёной сборки фронта и отсутствия новых ошибок API по сценарию; закрытые в финальном спринте хвосты (**K.107**, **L.119**, **K.112**, ручной **L.115**) зафиксированы в §A [DASHBOARD-REGRESSION-CHECKLIST.md](DASHBOARD-REGRESSION-CHECKLIST.md) (исторический 100+ backlog soft-retired → `trash/`). За границей MVP без отдельного ТЗ остаются, среди прочего: **C.27**, **C.33** (merge layout), **F.64**, расширение **F.57**, **E.50–E.52**, тема графиков **F.58**. **Wave 5 (платформа)** — старт с **I.86 / I.90 / I.92** (выбор 1–2 пунктов; **I.86** часто выносится отдельным спринтом), сверка **N.137–N.140** с кодом без массового рефакторинга, затем **H.77–H.82** после стабилизации реестра виджетов. **Wave 6** (**J, O, P, Q**) — по бэклогу и продуктовым инициативам, не смешивать с критерием готовности MVP дашборда.

**Приоритет цикла после MVP (2026-04):** по умолчанию для ближайших спринтов зафиксирован фокус **Wave 5** (I + сверка N + затем H). Переключение на **продуктовые ТЗ** (блок «Черновик ТЗ» в бэклоге) или на **качество/регресс** (чеклист + M) — по явному решению оператора; см. раздел **«Приоритет цикла после MVP»** в [DASHBOARD-REGRESSION-CHECKLIST.md](DASHBOARD-REGRESSION-CHECKLIST.md) (исторический 100+ backlog soft-retired → `trash/`).

- **Порядок внедрения бэклога дашборда:** для разработки зафиксирован **вариант B** (волны по зависимостям: оболочка и persist сетки → пресеты/тулбар → chrome плиток и данные → canvas/a11y/перф → платформа API/БД и безопасность → операции и Q). Внутри волны — по возрастанию номера пункта в [DASHBOARD-REGRESSION-CHECKLIST.md](DASHBOARD-REGRESSION-CHECKLIST.md) (исторический 100+ backlog soft-retired → `trash/`). Альтернатива — строгая линейная нумерация 1…175 (вариант A в плане Cursor plans dir (local IDE; not a monorepo SoT)).
- **Карточки** — прежний плиточный обзор здоровья и метрик. **`readiness_score`** учитывает заполненность ключевых артефактов и операций, средние показатели coverage/freshness и **`strategy_integrity_score`**. В **`counts`** для UI сводки отдаются **`open_alerts`** и **`critical_alerts`** (глобальные счётчики по проекту). Запрос **`GET .../projects/{project_id}/dashboard`** с **`compact_lists=true`** и без **`layout_id`** даёт более лёгкий JSON для разделов вне режима **`overview_dashboard`** (усечённые списки, без **`widget_list_slices`**); интерактивный дашборд использует полный бандл с **`layout_id`**. Свежесть блока «Исследования» опирается на **`MAX(updated_at)`** по карточкам исследований.
- **Метрика «Готовность»** (`readiness_score`) в UI — **не** тот же показатель, что плитка «Покрытие JTBD»: итог взвешивает заполненность артефактов, операции, **среднее** по всем шести метрикам блока `coverage` (в т.ч. сегменты, кампании, воронки, задачи), свежесть и связность стратегии. ## Модули проекта и права участников

### Поле `enabled_modules` (проект)

На проекте хранится список включённых модулей (slug’и из контура маркетинга: `jtbd`, `value_proposition`, `swot`, `competitors`, `researches`, `content_ai`, `segments`, `campaigns`, `funnel`, `tasks`, `alerts`, `ai_studio`, `amka`, `imc`, `imc_research`, `context_chat`, а также навигация `cabinet_overview`, `cabinet_companies`, `cabinet_projects`, служебный `__mc_none__`). Полный перечень и валидация — в `api/routers/projects.py` (`MC_MODULE_SLUGS_ALLOWED`).

**Старые проекты без новых slug’ов:** в БД колонка `projects.enabled_modules`. Добавить модуль для всех неархивных проектов можно миграцией в `shared/api/migrations/applied/` (пример: `20260327_01_projects_enabled_modules_imc.sql` — дописывает `imc` и `imc_research` без дублирования). Либо точечно: `PATCH /api/v1/projects/{id}` с объединённым списком `enabled_modules`. Лид/владелец после обновления видит раздел; участникам по-прежнему нужны права `mc_module:imc` (или аналогичные), если для них включён явный список прав.

**Что ещё может «не видеть» старый проект или пользователь (не только slug’и в БД):**

- На стенде **не применены** SQL-миграции (`20260320_01` — сегменты/кампании/воронка/задачи/алерты/AI Studio и др.; `20260325_02` — `client_interaction`; `20260327_01` — `imc` / `imc_research`) — тогда в `enabled_modules` нет соответствующих ключей.
- **Участник** (не лид и не владелец компании): видит пересечение `enabled_modules` с **`mc_module:*`**; если права выдавали давно узким списком, новых разделов не будет, пока лид не добавит `mc_module:<slug>` (или не расширит набор).
- **Мутации** (POST/PATCH/DELETE сущностей раздела): для участника требуется явное **`mc_module:<slug>`** того раздела (пустой `permissions` → **403**, без legacy «членство = полный write»). Лид и владелец компании — без этого ограничения. IMC: достаточно `mc_module:imc` **или** `mc_module:imc_research`. Карта роутер→slug: funnel, campaigns, researches, jtbd, value_proposition, competitors, segments, swot (`analysis`), ai_studio, amka, imc, client_interaction (+ customer diagnostic), content_ai (autofill/RAG), context_chat (tool-agent), tasks/alerts (`operations`). Dashboard layout остаётся на membership-gate без slug (shell). Реализация: `get_accessible_project(..., required_mc_module=…)` + `mc_module_acl.py`.
- **Представитель заказчика** без членства в проекте — отдельная ветка `cabinet_modules` (read-only), см. ниже.

**ИМК / `imc_research`:** в сайдбаре один пункт (`imc`); в `enabled_modules` допустимы оба slug — `imc` и `imc_research`. У участника в правах может быть только `mc_module:imc_research`; проверки UI не должны требовать подстроку только `'imc'` (см. `projectHasImcCabinetSlug` в `constants.ts`).

### Поле `cabinet_modules` в ответе API

Для **каждого** запроса проекта в ответ добавляется **`cabinet_modules`**: эффективный список модулей **для текущего зрителя**.

- **Руководитель проекта** (`viewer_id == project.created_by`) и **владелец компании** видят полный `enabled_modules`.
- **Участник** видит пересечение `enabled_modules` с разрешениями вида **`mc_module:<slug>`** и отдельными токенами навигации **`cabinet_*`**.
- Особое право **`can_upload_project_vault`** не открывает модули кабинета, но разрешает запись файлов в vault проекта (см. документацию файлового менеджера).

Логика: `compute_cabinet_modules` в `api/routers/projects.py`. На фронте `getMarketingSidebarModuleOrder` в `constants.ts` строит порядок пунктов сайдбара из `cabinet_modules` (или fallback `enabled_modules`).

### Управление командой

Управление участниками проекта — только **руководитель проекта**; приглашение участника требует **взаимной дружбы** (серверная проверка). Права задаются списком строк: `mc_module:…`, `can_upload_project_vault`, навигационные `cabinet_*`.

### Представитель компании без членства в проекте

Если пользователь только `representative_user_id` компании и не участник проекта, **`cabinet_modules` может быть пустым** — отдельная ветка в `_project_response_with_cabinet`.

**UI / shell (фронт):** оболочка окна опирается на `DesktopAppChrome` и `marketingCabinetDesktopVars.css` (`--mc-*` от `--desktop-accent-rgb`). Ширина основной колонки и секций — утилиты `mc-active-view-root` / `mc-section-root` (`--mc-content-max-width` по умолчанию **100%** — контент на всю ширину main между сайдбаром и краем); фон главной области и read-only баннер — `--mc-main-bg-gradient` / `--mc-readonly-banner-bg`; подписи блоков метаданных — `mc-meta-caption` + `text-(--desktop-text-muted)`. Шапка main (`MarketingCabinetContentFrame`) с `z-20` и панель «AI задачи» с повышенным `z-index`, чтобы выпадающий список не перекрывался скролл-контентом. Статусы и бейджи — по возможности через `--desktop-*`, без параллельной палитры `zinc/slate`. Индикаторы загрузки (`Loader2` и кольцевые спиннеры) используют `motion-safe:animate-spin motion-reduce:animate-none` для пользователей с `prefers-reduced-motion`. При ошибке `GET` списка компаний показывается баннер под тулбаром с текстом ошибки и «Повторить» (`cabinetPage.retryCompaniesLoad`); селект компании в тулбаре отключён, подписи плейсхолдеров — i18n (`toolbar.companiesUnavailable`, `marketingCabinetSelect.*`). Кнопка «наверх» в main учитывает `prefers-reduced-motion` (без `smooth` при reduce). Заголовки секций и ряд блоков выровнены с `DESKTOP_TYPOGRAPHY` там, где раньше был произвольный `text-[15px]`. В сайдбаре раздел «Ценностные предложения» использует иконку `BadgePercent`, «Кампании» — `Megaphone` (различие от дублирования одной иконки).

**Доступность (диалоги и навигация):** модалки с `role="dialog"` связывают заголовок и описание через `aria-labelledby` / `aria-describedby` (в т.ч. скрытая подсказка `modalKeyboardHint` про Escape/«Отмена»); ловушка фокуса Tab — `useMarketingDialogFocusTrap`. Панель AI jobs (`MarketingAiJobCenter`) — `aria-modal`, скрытые заголовок/описание из `jobCenter.dialogTitle` / `dialogDescription`, фокус при открытии на активном фильтре. Смена раздела сайдбара переводит фокус на заголовок текущего модуля в тулбаре (`#marketing-cabinet-module-title`, `tabIndex={-1}`), без кражи фокуса при первой отрисовке.
