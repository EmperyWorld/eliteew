# P1 — What EliteEW is

**Diagram:** [D01](assets/diagrams/D01-hybrid-formula.md)

## Formula

**EliteEW** is an organization work environment: a desktop with apps, files and
documents, projects on your own data, communication inside the contour, and AI
grounded in the organization’s materials.

It is a **managed work layer** on top of an ordinary device: work apps and files
live in the product, not as “just folders on a personal desktop.”  
It is **not** a host-OS replacement and **not** a sterile-disk promise.

It is also a **gift to the world**: first-party code is released under
`MIT` — you may run, study, modify, and share it under that
license ([P3c](03c-full-complex-source.md)). Software freedom is not a promise
of authors on staff, and it is not a promise of operated hosting.

## Host / DIY / EliteEW

| Axis | Host | DIY | EliteEW |
|------|------|-----|---------|
| Role | Familiar PC / server | Self-built stack | Work layer on the host |
| Stronger here | Drivers, local software | Build flexibility | One desk, apps, files, roles, session perimeter |
| Out of scope | — | — | Replacing the OS kernel “on every edition” |

## Who it is for

Anyone who needs **their own** work contour instead of a zoo of external
services — and who is ready to receive an open complex. How to live with the
gift: [P3e](03e-delivery-models.md). Editions: [P10](10-editions.md). Apps:
[P6](06-app-index-brief.md) / [P11](11-must-app-cards.md).

# P1a — Any device, including immersive displays

**Call / GAF detail:** P7a / P7b (here: any-device + immersive displays only)  
**Mobile subset:** P7e · **Desktop client:** P8

## Thesis

EliteEW opens wherever there is a modern **browser** contour — PC, laptop,
tablet in the browser, Android satellite, and also an **immersive headset**
(VR / XR) through the headset browser.

The product does **not** ship a separate “VR app from the headset store.”
Headset use is the **same web layer**: desk, apps, and internal video calls
(including from GAF Chat) when the headset browser, mic, and camera are usable.

**Checked:** the headset scenario was checked; **the headset model
is not named in public text**.

## Device map

| Contour | What you get | Not this |
|---------|--------------|----------|
| Browser (PC / laptop / tablet) | Full work layer in the browser | Host-OS replacement |
| Android satellite | Feed / chat / push subset ([P7e](07e-mobile-capability-matrix.md)) | Full desk as on desktop |
| Immersive headset browser | Web layer + internal calls when hardware allows | Native VR-OS · store app · “any headset without browser/mic/camera” |
| Tauri desktop client | Connected client contour ([P8](08-tauri-clients-ota.md)) | A second product tree |

## Honest framing

| | |
|--|--|
| **Present** | Browser access · Android satellite · calls = web/WebRTC contour · headset checked without model name |
| **Checked** | Headset browser path for product web UI and internal calls |
| **Not promised** | Native VR-OS · headset store listing · “every headset works offline without a browser” · phone = full EliteEW |

# P2 — Threats and protection

**Diagram:** [D02](assets/diagrams/D02-threat-classes.md)

## The problem (channel, not people)

A common leak path: personal messengers, personal clouds, paste into an external
AI. A VPN closes a pipe but does not see inside a personal app. Classic endpoint
DLP often wants an agent — fragile on BYOD.

EliteEW is a **fast lever** on top of the current security stack: separate work
from personal. It does **not** replace firewall / antivirus / full DLP.

## Threat classes → product response

| Class | What happens | EliteEW response |
|-------|--------------|------------------|
| Shadow IT / personal messenger | Work files leave into a personal channel | Work chat/files inside the contour (P7a) |
| Personal clouds | Copy outside org control | Files in the managed library (P4a) |
| Paste / external AI | Strategy fragments leave | AI and materials stay in the project contour (P5b) |
| BYOD without separation | Personal OS = work desk | Browser / APK layer without an admin agent on the personal OS |
| Open exposure | Services open to everyone | Edge / granted trust (P7d) |
| Untrusted device / OTA | Client substitution | Client trust boundaries (P8) |
| Insider / roles | Excess rights | Org/project roles (P5a) |
| Screen photo | Analog channel | Digital-channel minimization — not 100% (P12) |
| “Sterile disk on every edition” | No traces on personal disk | Not a universal promise (P12) |

Host / DIY / EliteEW comparison — [P1](01-what-is-eliteew.md); limits — [P12](12-honest-limits.md).

**Diagram:** [D03 — norms: contributes / stays](assets/diagrams/D03-npa-split.md)

## Important

This chapter is an **orientation map** for security and counsel dialogue inside
the organization. EliteEW **helps** close an organizational-technical contour
(data separation, access, roles, perimeter). It does **not** replace
certification, protective-tool licensing, impact assessment, or internal policy.

**Forbidden in this pack:** claims of “already certified,” “full legal compliance
out of the box,” guarantees about fines or lawsuits.

Current wording of norms is checked by the organization’s own counsel.

## Orientations (meaning map)

| Orientation | Topic | What EliteEW contributes | What stays with the organization |
|-------------|-------|--------------------------|----------------------------------|
| Information protection | Contour and access | Managed perimeter, roles, work-layer access control | Threat model, certification, tool choice, org measures |
| Cross-border data | Where personal data goes | Storage and work in the **chosen** edition contour (cloud / on-prem) | Legal bases, contracts, registers |
| AI use | Transparency and control | Project-data AI inside the contour; access policies (P5b) | AI policy, risk assessment, operator responsibility |
| Personal data | Protection and separation | Technical separation and access levers | Data controller duties, consents, localization by model |

# P3c — The complex, open source, gift to the world

## Core idea

EliteEW is given to the world as **free software**. First-party code defaults to
`MIT` (repository root `LICENSE`). That is about **freedom to use
and share**, not about a tariff for “opening the repo.”

1. **A full complex** — not “one chat” and not “one drive”: desk, apps, files,
   communications, AI, mobile companion, editions (cloud / on-prem / client) in
   one platform.
2. **Your instance** — a deployed organizational contour stays **yours**
   (especially on-prem), not a shared demo account.
3. **Free source** — you may run, study, modify, and redistribute first-party
   code under MIT. Public source reference:
   [github.com/EmperyWorld/eliteew](https://github.com/EmperyWorld/eliteew)
   (see also the platform license map).
4. **MIT terms** — preserve the copyright and permission notice in copies or
   substantial portions of the software. MIT does not require publishing
   modifications or source code for network services.
5. **Not one license for the whole tree** — first-party default is
   MIT; explicit component notices and third-party components
   keep their own SPDX / NOTICE / SBOM. Map:
   `documentation/platform/THIRD-PARTY-LICENSE-MAP.md`.

## What MIT does not move

The EliteEW name and logo are not “part of MIT.” Forks and modifications follow
the code license; presenting a fork as official EliteEW without a separate mark
agreement is out of scope.

How to live with the gift in practice — [P3e](03e-delivery-models.md).  
How to accept release artifacts in-house — [P3f](03f-transfer-bom-handover.md).

# P3d — Self-host cost structure (orientation)

**Diagram:** [D09](assets/diagrams/D09-tco-columns.md)

## Disclaimer

Below is a **structure** of cost lines when the organization runs the contour
**itself**. Not a service tariff, not a monetary valuation of the gift, not an
ROI formula. The MIT gift is about code freedom; costs appear in host, people,
and operations.

## Cost lines

| Line | Typical desktop contour | Self-host DIY | EliteEW self-host |
|------|-------------------------|---------------|-------------------|
| Host OS / devices | OS licenses / PC updates | Hardware + OS support | Host stays; layer is the contour profile |
| Agent DLP/EDR on BYOD | Licenses + conflict | Similar | No admin agent required on personal OS (P2a) |
| External service zoo | Many subscriptions | Self-host + payroll | Unified app contour |
| Standing the contour up | Long agent path | Long DIY build | After access — minutes to days (orientation) |
| Support | Agent/software helpdesk | High DIY payroll | Your service / integrator |
| Shadow IT risk | High without a layer | High without a layer | Separation layer (P2) — not zero risk |

## How to read

The gift does not zero payroll. The point is less zoo and less BYOD agent
conflict **if** scenarios truly consolidate into EliteEW. Concrete numbers stay
outside this pack.

| Axis | Host | DIY | EliteEW |
|------|------|-----|---------|
| Cost driver | OS + agents + SaaS | Build payroll | Host + people on the contour |
| Trap | Shadow IT | “Free” ≠ cheap in payroll | Role discipline required |

# P3e — Gift to the world: how to use the open complex

**Diagram:** [D11](assets/diagrams/D11-gift-to-world.md)

## Center of gravity

EliteEW is a **gift to the world** as free software. The primary path is to take
first-party code under `MIT`, run your own contour, and evolve it.
Software freedom ≠ authors on staff, SLA, or the official brand “included.”

| Path | Meaning |
|------|---------|
| **Self-hosted under MIT** | Run, study, modify, redistribute first-party code; no fee for “the right to open the repository” |
| **Your on-prem / isolated contour** | The same gift, deployed by the organization (IT or an integrator) |
| **Hosted / hands-on help (optional)** | Someone may help operate or accept a release — that is **accompaniment**, not a replacement for MIT and not a way to enclose the source |
| **Name and mark** | MIT does not transfer EliteEW brand rights; putting your own brand on top is a separate mark topic |

1. **Your work perimeter** — desk, files, communications, roles, mobile companion.
2. **Data control** where a private contour is required ([P3](03-regulatory-map.md)).

# P3f — Receiving the gift in-house (artifacts · Day‑0…90)

**Diagram:** [D12](assets/diagrams/D12-transfer-handover.md)  
**Gift & license:** [P3c](03c-full-complex-source.md) · **how to use it:** [P3e](03e-delivery-models.md)  
**Do not confuse with:** an operator ops runbook · end-user CLI · “someone else’s production secrets in a zip”

## Why this chapter exists

The code is already open under MIT. An organization needs a practical answer:
**which artifacts to verify**, what will never arrive with a contour handoff, and
how to stand up your own instance in the first weeks without mistaking the gift
for perpetual author staffing.

## Artifact classes (not a secret manifest)

Guidance for self-host / on-prem due diligence. The MIT right to use first-party
code does **not** depend on this list.

| Class | Usually present | Usually absent |
|-------|-----------------|----------------|
| Source | Public MIT source + release commit/tag | Foreign SaaS accounts, foreign personal data, foreign keys |
| Documentation | Current product/platform canon for evolution | Internal drafts, agent dialect notes |
| Build | Build recipes, test contours without prod secrets | Passwords, host keys, live SOPS bundles |
| Sample config | Scrubbed templates / edition profiles | Live URLs/IPs, another operator’s IdP client ids |
| Clients | Desktop / mobile sources or artifacts in an agreed scope | Foreign store certificates without a separate transfer |
| Knowledge | Agreed knowledge sessions — **only if** accompaniment was arranged | A promise of “authors forever” |
| Brand | Only if mark use was separately agreed | Automatic right to present a fork as official EliteEW |

**Rights:** first-party default is `MIT`; explicit component notices and
third-party components keep their own licenses (third-party map + release SBOM).
Marks and names are separate. This pack is **not** a legal opinion.

## “Day of acceptance” logic

1. Public source link and exact commit/tag (+ agreed binaries if needed).
2. Checklist of the classes above (not end-user CLI).
3. If accompaniment exists — a contact for the acceptance window (not “eternal user support”).
4. An implementation architect / mentor — **only** if separately arranged ([P3e](03e-delivery-models.md)).

## Day‑0…90 orientation

Timing depends on IT/integrator maturity and edition. Numbers are orientation,
not a contractual SLA.

| Phase | Orientation | Focus | Outcome |
|-------|-------------|-------|---------|
| **H0 Verify artifacts** | Day 0–14 | Source, commit/tag, builds, docs | “What we need for our stand is here” |
| **H1 First stand** | Day 14–45 | Your instance, IdP, role smoke | A live stand **you** own |
| **H2 Pilot** | Day 30–75 | One unit: desk, files, chat, roles ([P3a](03a-employee-day-adoption.md)) | A proven employee day |
| **H3 Scale** | Day 60–90+ | Your service runbooks ([P10c](10c-ops-scale-not-user-cli.md)) | Ops without end-user CLI |
| **H4 Stabilize** | per your plan | Edition criteria + needed apps | The contour lives with you |

Migration from a tool zoo — [P3g](03g-si-migration-playbook.md).

# P7c — Trusted phone and on-device E2EE keys

## Thesis

With **trusted phone binding**, separate key families can appear on the device:

| Family | Purpose | Private key |
|--------|---------|-------------|
| Device identity | Prove “same phone” | On the phone |
| Secure Connection channel | Enter the protected perimeter | On the phone |
| **GAF E2EE** | End-to-end chat encryption | On the phone |

The server keeps **public** material and message ciphertext; it does **not**
recover a lost GAF private key. Lose the key without a transfer path = old E2EE
messages are unreadable from the server.

**Turning E2EE on in a chat :** not by default; needs mutual consent and
ready trusted devices with keys. While E2EE is active, ordinary plaintext is
not accepted into that chat.

**Not promised:** “all chats always E2EE” · “the server holds the decryption secret” ·
“E2EE = the same key as WireGuard.”

Comparisons — [P1](01-what-is-eliteew.md); limits — [P12](12-honest-limits.md).

# P9 — Capsules and place access

**Boundary:** a capsule / seat is **service access** to a hosted or trusted
channel. It is **not** a code license and does **not** cancel the MIT gift of
self-hosting.

If the organization uses official cloud, a managed contour, or a trusted place
connection, access is issued as an **access file (capsule)**: an operator
issues it, the user imports it — without “storefront self-registration of a
key.” Self-hosted first-party MIT launch does **not** require a capsule.

Place modes: **offline** / **cloud** / **both**.

A capsule carries place trust; it is **not** a chat E2EE key and **not** an IdP password.

---

# P9a — Service access and sealed materials

In older API names, “license” here means a **service entitlement**: access to
hosted features, managed functions, or a trusted channel. That is **not** the
MIT code license and does **not** block self-hosted use of the gift.

| Rule | Meaning |
|------|---------|
| Control | Entitlement can be revoked / time-bounded / capability-narrowed where supported |
| At rest | Storage keeps a **hash** / sealed materials — not everlasting plaintext keys as the norm |
| Issuance | An access secret may appear **once** at issuance; then the capsule |
| UX | Import a **sealed** capsule; not “paste a key into Notepad” as the main path |
| Client | Place private material stays in the OS-protected store, not in JS/logs |

We do **not** promise: users must edit conf by hand · the server stores chat
private keys · a capsule is a password to every service in the world.

# P12 — Honest limits

So capabilities are not confused with absolutes. Below is what must **not** be
promised “for every edition at once.”

| Topic | Say this | Do not say this |
|-------|----------|-----------------|
| Sterile disk / wipe | Edition policy; verify on PoC | “We guarantee a sterile disk everywhere” |
| UI latency | Comfort orientation on PoC | “Always ≤200 ms for everyone” |
| Screen photos | Digital-channel minimization, not 100% | “Screen capture is impossible” |
| FoFline = air-gap | No: local pack + channel ([P10](10-editions.md)) | “Full air-gap” |
| Replacing firewall/AV/DLP | A layer on the stack ([P2](02-threats-and-protection.md)) | “We replace the whole security stack” |
| AI replaces experts | Speeds drafts on your data | “Replaces the team” |
| Multiple song studios | Current: **MusicForge** (+ player) | Several equal active studios |
| Phone = full desk | Subset ([P7e](07e-mobile-capability-matrix.md)) | “All of EliteEW in a pocket” |
| Always E2EE | By consent ([P7c](07c-trusted-phone-e2ee.md)) | “Always E2EE” |
| Self-host costs | Payroll/host orientation ([P3d](03d-tco-orientative.md)) | “The gift means zero cost forever” |
| External messenger as entry | Not a primary product channel ([P10d](10d-external-messenger-honesty.md)) | “This is our main entry” |
| Certification out of the box | Forbidden ([P3](03-regulatory-map.md)) | “Already certified” |
| Authors “inside the gift” | No ([P3e](03e-delivery-models.md)) | “Authors will run you for years” |
| MIT = whole monorepo | First-party default; exceptions and third-party separate ([P3c](03c-full-complex-source.md)) | “Everything in the repo is one license” |

# Overview: gift to the world and your contour

A short page for people deciding whether to **receive EliteEW** as an open work

## What it is

**EliteEW** = the organization’s work desk (apps, files, projects, AI on your data)
