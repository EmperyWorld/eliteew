# EWA companion workflow engine v2

Reference · source contract reviewed 2026-10-11. Engine v2 represents personal workflows as a bounded directed acyclic graph with UUID nodes, explicit edges and a per-run output registry. This guide owns graph validation, node bindings, the in-process runner, durable DAG execution/resume and the visual builder. [Personal workflows](EWA-COMPANION-USER-WORKFLOWS.md) owns OAuth CRUD, phrase matching and linear v1 behavior; [workflow registry](EWA-COMPANION-WORKFLOW-REGISTRY.md) owns operator/builtin selection. Source implementation and mock-backed checks do not certify deployed worker/provider behavior.

## Definitions and graph order

The canonical [Pydantic model](../../../shared/api/ewa_platform/schemas/pydantic/companion_workflow_v2.py) requires schema_version=2, workflow_id matching ^[a-z][a-z0-9_]{2,63}$, version>=1, nonempty RU/EN titles, at least one trigger and 1–10 nodes. enabled defaults false. Description, tags, env_gate and execution_mode are metadata; async is the execution-mode default. A stored personal row id is separate from definition.workflow_id and its version.

Each node has a UUID id, one of 20 types, mode (stateful default), config, inputs, input_specs, outputs, on_error and optional titles. Output/input spec types are string, text, json, boolean, number and image_url. The model validates unique ids, edge endpoints, self-edges, fallback configuration and orphan layout ids. It does not prove runtime output values match declared types or that every required input is supplied.

Edges have source_node_id, target_node_id, optional branch and mapping_rules. [Graph helpers](../../../shared/api/ewa_platform/companion/workflows/dag/graph.py) build forward/reverse adjacency and use Kahn ordering with lexicographically sorted UUID ties. Cycles fail execution preflight; disconnected zero-indegree nodes are legitimate entrypoints and run in that order. The model alone does not reject a cycle or duplicate edge. A graph dependency is not a parallel scheduler: ordinary nodes execute sequentially.

builder_meta has its own schema_version=1, node_positions keyed by node UUID and optional viewport. It is saved inside definition_json and ignored by execution. Positions are floats; viewport is a float mapping, not backend validation of all React Flow x/y/zoom semantics. Moving a node does not change graph dependency order.

## Validation and data flow

[Preflight](../../../shared/api/ewa_platform/companion/workflows/dag/validation.py) runs quota, graph, placeholder, declared-type, outbound, branch, loop, transform and expression checks in sequence, stopping subsequent stages after errors. [Tier limits](../../../shared/api/ewa_platform/companion/workflows/dag/limits.py) are 3 nodes for regular users and 10 for verified users, within the model's ten-node cap. HTTP validate-v2 takes verification from OAuth User.is_verified; runners use ToolContext.auth_user. Personal CRUD currently hardcodes an unverified context in its save helper, so a verified four-node graph can pass validate-v2 and fail save (DOC-CODE-080).

[Resolver](../../../shared/api/ewa_platform/companion/workflows/dag/variable_resolver.py) supports {{turn.user_line}}, {{turn.principal_id}} and {{<node-uuid>.<output-field>}} with nested object fields. A whole-string placeholder preserves its underlying value; interpolation inside other text uses string(value). Lists are not indexed through path components. Missing/None paths raise UnresolvedPlaceholderError. The node must declare a referenced output field for type validation, but executor outputs are not checked against that declaration at runtime.

Placeholder checks cover node.inputs and incoming edge mapping_rules. Allowed source nodes are all already seen in topological traversal plus direct upstream nodes; the backend therefore permits some earlier disconnected sources, rather than enforcing strict transitive ancestry. The UI picker is narrower and lists actual transitive ancestors. Config-expression checks validate syntax separately and do not establish the same output-declaration/ancestry contract. Loop preflight allows only loop.item/index/total/id; runtime can descend into item mappings, which is a distinct boundary.

Every incoming edge mapping is resolved eagerly in definition edge order. Later mappings win the same key; node.inputs then wins over all edge values, including an empty authored string. An invalid shadowed edge placeholder can still fail before node input wins. Explicit input_specs or type/profile defaults supply expected types where available; unknown input keys can have no expected type. json/number/boolean may feed text/string, text and string interoperate, and image_url only matches image_url. Literal values, required=true presence and actual output schemas are not universally enforced.

[State registry](../../../shared/api/ewa_platform/companion/workflows/dag/state_registry.py) stores shallow per-node output mappings and turn identity, plus an in-memory loop frame stack. Its snapshot excludes loop frames. [Context switcher](../../../shared/api/ewa_platform/companion/workflows/dag/context_switcher.py) clears shell_norm, intent_plan, profile and image_attachment for stateless nodes while retaining principal/catalog identity, pools, bearer/auth information and the user line. Stateful uses the base context. These modes do not themselves impose access control, isolate side effects or provide a distinct model backend.

## Node types and actual bindings

[Binding registry](../../../shared/api/ewa_platform/companion/workflows/dag/dag_tool_bindings.py) owns tool-backed types, profiles and confirmation annotations. [Executors](../../../shared/api/ewa_platform/companion/workflows/dag/executors.py) own inline behavior. There are eleven tool-backed types and nine inline types:

- prompt_gen returns a local `[prompt_gen stub]` reply. temperature/max_tokens/top_p appear in its output; it does not call an LLM.
- api_call resolves config.tool_name from the companion tool registry and personal allowlist. It is not an arbitrary HTTP client. Other tool-backed types also accept a registered, allowlisted config.tool_name override.
- image_gen defaults to image_generation; document_import to paperless_import; pdf_generate to presentation_generation. The last is the presentation child workflow binding, not an unconditional synchronous PDF generator.
- telegram_sender and email_dispatcher default to their same-named outbound tools and carry requires_confirm_gate metadata.
- vision_analyzer binds vision_analyze, llm_summarizer binds llm_summarize and llm_classifier binds llm_classify. pdf_parser and document_extractor bind their same-named tools. Each uses its corresponding AI/document IO profile; node type and registry tool name are distinct contracts.
- logic_filter returns matched based on text/contains but does not stop the graph when false. Use decision/switch for routing.
- confirm_gate returns needs_confirm with message/confirmed=false. Durable handling pauses; the library runner currently continues (DOC-CODE-088).
- delay is an immediate marker in the library. Durable handling schedules a countdown task and processes a later wakeup.
- decision chooses yes/no from a structured condition or expression; switch chooses the first matching case, otherwise default.
- print_log logs its resolved text and returns reply/text/log metadata. Workflow content can therefore enter debug logs.
- for_each runs its body inline through the loop helper, including inside a durable node task. It is not a separate queued task for each item/body node.
- data_transformer applies an allowlisted local transform and returns reply/text/value.

The default executor registry also contains internal echo/constant helpers, but these are not accepted node types in the public v2 model. Binding annotations such as stateful_required/stateless_ok are metadata; the adapter does not universally enforce those mode annotations.

[Tool adapter](../../../shared/api/ewa_platform/companion/workflows/dag/tool_registry_adapter.py) builds arguments from resolved inputs, supplies a user line, router bypass and server parent-run/step links, sanitizes public tool keys, then applies the node type's [IO profile](../../../shared/api/ewa_platform/companion/workflows/dag/dag_io_profiles.py). Descriptor keys filter public fields, while underscore fields survive. Reply, selected tool data, child ids/status and profile fields become DAG outputs; tool client actions are not delivered through this projection. Output declarations are not a runtime filter/type validator.

When EWA_COMPANION_DAG_TOOL_REGISTRY_ADAPTER_ENABLED is false (source default), tool-backed executors return synthetic outputs. Examples include stub:// media URLs, fabricated document ids and delivery_status=sent without delivery. pdf_generate returns accepted with a synthetic child id. A completed stub chain is a library test result, not a generated file, live import or outbound receipt. prompt_gen remains a stub even when that adapter flag is true.

## Outbound, AI and document boundaries

[Outbound policy](../../../shared/api/ewa_platform/companion/workflows/dag/dag_outbound_policy.py) requires any transitive confirm_gate ancestor for literal telegram_sender/email_dispatcher node types. It does not require a gate on every path and does not inspect the resolved config.tool_name. With the strict guard enabled, those typed bindings need an ancestor's confirmed=True (or accepted true string) in the registry; with it disabled, the adapter sets outbound authorization for typed send bindings automatically.

User-authored api_call inputs currently retain _dag_outbound_authorized through the reserved argument path. Combined with config.tool_name=email_dispatcher, both validation and the strict type-based guard miss the send binding, and the real handler can reach the send function without a gate (DOC-CODE-087). That finding was verified with a mocked send boundary; no email or Telegram message was sent. These checks must not be described as universal tool confirmation enforcement. [Public confirmation](../../../shared/api/ewa_platform/companion/workflows/action/confirm_flow.py) also retains the separately recorded claim-state loss in DOC-CODE-036; direct helper tests do not prove the public recovery path works.

[AI services](../../../shared/api/ewa_platform/companion/workflows/dag/workflow_ai_services.py) use the existing companion LLM runtime and HTTP compatibility transport. Summarizer/classifier/vision prompt input caps default to 24000/8000/2000 characters, clamped to 256–128000. Truncation occurs at the service boundary, while DAG outputs can retain larger source text. Those services use their own temperature/token settings (summarizer .15/2048, classifier 0/256, vision .2/1024); the inspector's generic LLM config does not prove it controls these calls.

Vision resolves explicit base64 attachments, image URL, or a matching context attachment id, then uses multimodal content or OCR fallback according to companion vision flags. URL fetch follows redirects with a 30-second timeout and checks 4 MiB after loading response.content, plus MIME magic. The inspected helper does not establish a general URL destination allowlist or streaming download cap; a mocked internal-URL probe is recorded in DOC-CODE-101. Classifier parses category/matched lines from model text; it does not validate category membership against an enum of supplied labels.

[Document services](../../../shared/api/ewa_platform/companion/workflows/dag/workflow_document_services.py) prefer file_base64, then unified_content_id/document_id, then positive paperless_id. Catalog bytes come from application DB/storage; Paperless bytes come from its gateway. PDF text extraction uses Tika and OCR fallback for empty text; text/plain/TXT can decode locally, while other supported document suffixes use Tika. Results include text/extracted_text, filename, MIME, char_count and optional page_count/error. Suffix checks and empty/error handling are narrower than a full file-format validation guarantee.

The catalog-byte query currently selects by id/deleted_at without any owner/principal predicate and ignores ToolContext at this service boundary (DOC-CODE-092). Worker tool context also assigns the EWA orchestration pool as main_pool; handlers preferring main_pool can reach the wrong DB contour (DOC-CODE-091). These are recorded code issues, not documented permission to access another user's content or to repair infrastructure during this docs task.

## Branches, expressions and transforms

[Branch validation](../../../shared/api/ewa_platform/companion/workflows/dag/dag_branch_validation.py) requires at least two labeled outbound edges for decision/switch, checks label duplication and decision yes/no, and checks switch cases against labels. Unlabeled edges can remain and are not counted as branches. Runtime skips the unselected branch's reachable nodes while preserving nodes reachable from the selected branch, including merges. Skipping is a graph calculation, not universal validation that every later required output exists.

[Expression evaluator](../../../shared/api/ewa_platform/companion/workflows/dag/dag_expression.py) implements comparisons, AND/OR/NOT and len/string_length/empty without eval. Its current logical splitting is not aware of parentheses or quoted strings: `false AND (false OR true)` and `"x OR y" == "other"` both evaluate true (DOC-CODE-096). Treat the supported syntax as limited; do not claim a general boolean parser with grouping. Syntax preflight does not prove correct runtime routing for all accepted expressions.

[Transforms](../../../shared/api/ewa_platform/companion/workflows/dag/dag_data_transform.py) support identity, json_stringify, json_parse, string_trim/lower/upper/replace/slice, array_filter_contains, array_length and pick_field. The source value is the first nonempty value/text/input/body/reply. String operations coerce values, replace needs find, slice accepts integer indices, array filtering needs a list/needle, and pick_field reads one object key. The validator checks operation membership; malformed runtime data/args can still fail. Transform errors become NodeExecutionError at the executor boundary and can enter on_error handling.

## Loop execution

[Loop validation](../../../shared/api/ewa_platform/companion/workflows/dag/dag_loop_validation.py) requires one body branch entry and a nonempty graph body. A next branch identifies continuation; reachable next nodes are subtracted from the body. Nested-loop detection produces warnings rather than a hard rejection. [Loop helper](../../../shared/api/ewa_platform/companion/workflows/dag/dag_loop.py) coerces input into items: lists/tuples, JSON-array strings, comma-separated strings, one scalar or an empty list. It pushes item/index/total/id, executes body nodes sequentially and returns count/items_processed/iteration_results.

The UI exposes max_iterations, but the backend model drops that field and the loop has no item cap (DOC-CODE-095). Node-count quota does not bound loop iterations, repeated side effects or stored result size. Body outputs share one registry across iterations and iteration_results retains item/body output data. A body accepted/needs_confirm result becomes loop failure; it does not establish a durable per-item child/confirmation pause. Body execution calls the single-attempt helper, rather than applying each body's own on_error wrapper.

Durable loop success marks all body ids completed/ok, including a zero-item body that never ran. Branch skips and loop body completion currently update DAG state without synchronizing corresponding SQL step rows. The general worker's prior-step guard can then block continuation on a pending body/skipped row (DOC-CODE-093). This is why a direct node-handler test is insufficient for full queued-loop acceptance.

## Library runner versus durable execution

[Library runner](../../../shared/api/ewa_platform/companion/workflows/dag/runner.py) performs preflight, creates an in-memory registry and walks ordered nodes. stop records a failed node and skips its transitive downstream; independent nodes can still execute. retry repeats immediately in process (max_attempts clamped 1–5, default 3); fallback_value registers the supplied mapping and counts success without runtime output type checks. Branch skips are distinguished from failure skips in terminal status calculation.

Library result statuses are invalid/completed/partial/failed, with ordered/completed/skipped ids, registry_snapshot, node_outcomes, failed_node_id and error. accepted/needs_confirm currently count as completed nodes and allow later execution; no child wait or user approval occurs in this runner. Variable resolution happens outside the executor's NodeExecutionError catch, so a missing declared upstream value can raise UnresolvedPlaceholderError past retry/fallback instead of returning DagRunResult (DOC-CODE-089). The sync wrapper uses asyncio.run and is not suitable inside an already running event loop.

[Durable starter](../../../shared/api/ewa_platform/companion/workflows/dag/dag_workflow_starter.py) requires the master, DAG Celery and v2 flags. After preflight it checks a bounded active-run selection for the same personal row, creates an action_workflow_v2 run, snapshots the full definition in plan_payload, creates dag_node steps for every ordered node, best-effort caches bearer/OAuth/profile information and enqueues the first step. execution_mode=sync does not bypass this queue path. The snapshot pins v2 definition content for that run, unlike the personal v1 continuation loader.

[State store](../../../shared/api/ewa_platform/companion/workflows/dag/dag_state_store.py) persists dag_engine=v2 and dag_state with ordered/pending/completed/skipped ids, current node, registry outputs, outcomes, failure/error, user line and catalog identity. The loop stack is not persisted. Full definition, registry, step output and terminal result can duplicate content; service input truncation does not imply a bounded PG payload or complete retention policy.

[Node handler](../../../shared/api/ewa_platform/companion/workflows/dag/dag_node_executor.py) runs under the [general job executor](../../../shared/api/ewa_platform/companion/jobs/executor.py) and dag_node registration in [step handlers](../../../shared/api/ewa_platform/companion/jobs/step_handlers.py). Ordinary success updates step/output, writes plan under expected revision and queues the next pending node. for_each runs all body work inside its node task. Child accepted leaves the step in_progress and parent running; needs_confirm puts the step/parent awaiting_confirmation with a DAG gate descriptor. Returned client actions are not accumulated into a whole-workflow response.

Delay first resolves/clamps seconds to 0–3600 and queues a wakeup without sleeping the worker. Wakeup currently records config.delay_sec as delayed_sec, even if the countdown came from a different resolved delay_sec input; this differs from the inline output key (DOC-CODE-094). Persistence and subsequent enqueue are separate operations. A failed next-node enqueue raises after committed node/plan updates, while replaying the completed step is short-circuited by the outer worker (DOC-CODE-097). No transactional outbox/automatic recovery guarantee is established by this path.

Terminal DAG status is computed as completed/partial/failed; SQL parent status maps partial to completed and keeps the finer result_payload.dag_status/error. Finalization does not use expect_revision. A stopped durable node terminalizes immediately rather than running every independent remaining node as the library can. Task/step events are published, but storage/event/queue writes are not one atomic transaction.

[Async resume](../../../shared/api/ewa_platform/companion/workflows/dag/dag_async_resume.py) uses parent run/step links to project child outputs, complete the node and schedule continuation. Successful advance retries three revision conflicts, then attempts a two-second reconcile job; an enqueue failure is logged and returns false, so the mechanism is not a proof of guaranteed eventual delivery. Step/event updates precede the successful parent CAS. Failure/finalization paths have different revision/terminal guards. The inspected callback assumes trusted linkage from its caller; this guide does not certify every provider's ownership, delivery or retry path.

## HTTP and feature switches

POST /api/v1/ewa/companion-user-workflows/validate-v2 is OAuth-protected and accepts `{"definition": <complete-v2-definition>}`. It returns ok, workflow_id/version, node/edge counts, max_nodes_allowed, ordered/entrypoint ids, errors and warnings. It is a validation operation, not an execution request or an orchestration-pool health check. Model-invalid outer bodies return 422; raw-definition validation reports errors, while some malformed raw version reporting can escape (DOC-CODE-041). The [personal guide](EWA-COMPANION-USER-WORKFLOWS.md) specifies CRUD auth/errors and save payload: name/enabled/phrase trigger plus dag={nodes,edges,builder_meta,execution_mode}.

[Configuration](../../../shared/api/ewa_platform/companion/workflows/config.py) reads source environment flags. EWA_COMPANION_USER_WORKFLOWS_ENABLED defaults true independently of the action master. EWA_COMPANION_WF_ENGINE_ENABLED defaults false; EWA_COMPANION_DAG_CELERY_ORCHESTRATION_ENABLED and EWA_COMPANION_WORKFLOW_ENGINE_V2_ENABLED default false and require the master/Celery chain. The tool adapter is separately default false and does not itself require the master.

Telegram/email, strict outbound, vision/summarizer/classifier and PDF parser/document extractor subflags default false and require the master. EWA_COMPANION_WF_DATA_TRANSFORMER_ENABLED defaults true but still requires the master. Changing only the v2 switch does not prove real tool dispatch, provider readiness, queue routing or confirmation enforcement. No environment values or deployment state were read for this audit. [Current topology](../../platform/PRODUCTION-TOPOLOGY-STATE.md#current-2026-07-30--living) remains the single deployment state reference.

## Visual builder and authoring limits

[Builder shell](../../../shared/web/frontend/src/features/ewa/companionWorkflowDagBuilder/CompanionWorkflowDagBuilderMode.tsx) keeps semantic nodes/edges separately from React Flow display nodes/edges. The 20-node-type palette supports click/drag, selection routes to node/edge inspector, removal updates semantic dependencies, and save maps layout to builder_meta. No default node is inserted into a new empty canvas. [Canvas mapping](../../../shared/web/frontend/src/features/ewa/companionWorkflowDagBuilder/mapping/canvasMapping.ts) saves execution_mode=async, preserves loaded metadata and supplies default positions when absent.

[Load/save hook](../../../shared/web/frontend/src/features/ewa/companionWorkflowDagBuilder/useCompanionDagBuilderLoadSave.ts) loads an edit or duplicate source, redirects legacy v1 to the list, and retries failed loads. Edit wins conflicting edit/duplicate ids. Duplicate uses a copy name and POST. Name/phrase/node presence is checked locally; the hook sends a complete preview definition to validate-v2, maps error strings, updates the displayed quota, then POST/PATCH saves enabled=true with a phrase trigger. Warnings are not shown by this save path. There is no execution button or successful provider check in that validation sequence.

The initial UI cap is ten until a validation response supplies the actual tier. Existing metadata-only editing can rebuild only the first trigger phrase and force enabled=true/async. [Dirty state](../../../shared/web/frontend/src/features/ewa/companionWorkflowDagBuilder/state/dagBuilderDirtyState.ts) compares trimmed name/phrase and semantic nodes/edges, excluding positions/viewport. Explicit back/exit asks window.confirm when dirty; it is not a general browser-close/navigation guard. Preset loading currently sets the loaded graph as the clean baseline before any persistence (DOC-CODE-099).

[Properties](../../../shared/web/frontend/src/features/ewa/companionWorkflowDagBuilder/panels/DagNodePropertiesPanel.tsx) uses [field schemas](../../../shared/web/frontend/src/features/ewa/companionWorkflowDagBuilder/registry/fieldSchemas.ts) and local/server fallback catalog data. It patches inputs as strings, config numeric fields as Number(value)||0, and offers error strategy/attempt fields without a fallback_outputs editor. api_call exposes tool choice but generic profile has no own input fields. Existing typed input/output/config fields are therefore not all authorable through this inspector. Selecting a tool does not dynamically expose its catalog argument schema.

[Edge panel](../../../shared/web/frontend/src/features/ewa/companionWorkflowDagBuilder/panels/DagEdgeMappingPanel.tsx) edits arbitrary mapping keys and displays a branch label if already present. It has no branch-label control; connectEdge creates unlabeled edges, so new decision/switch/loop routes cannot be completed through this canvas path alone (DOC-CODE-100). The panel warns about conflicts only for nonempty node.inputs, whereas backend precedence includes empty strings. Loaded branch metadata can be preserved without proving all branch graphs can be authored interactively.

[Variable picker](../../../shared/web/frontend/src/features/ewa/companionWorkflowDagBuilder/graph/buildVariablePickerTree.ts) offers turn fields, transitive upstream declared/profile outputs and loop fields inside a detected body. Insertion appends to the current field; the exported cursor helper is not used by the picker controller. No semantic output type checking occurs simply because a picker value was inserted.

Four [presets](../../../shared/web/frontend/src/features/ewa/companionWorkflowDagBuilder/registry/dagWorkflowPresets.ts) provide document summary (2 nodes), PDF summary (3), PDF summary email (4), and prompt/log (2). [Loader](../../../shared/web/frontend/src/features/ewa/companionWorkflowDagBuilder/presets/loadWorkflowPreset.ts) remaps ids and supported placeholders, replaces the graph after a populated-workspace confirmation and applies suggested names/phrases. The email preset has no confirm_gate and fails current backend validation even for a verified user (DOC-CODE-098). Paperless id zero and example recipient fields require real author input; a preset title is not an accepted automation.

## Verification and implementation work

Existing core DAG/adapter/binding/loop/logic selection passed 59 tests. Outbound/content/AI/Celery/OCC selection passed 50; a separate mock-backed async-resume scenario passed one (its direct global executor mutation was isolated to that process). Eleven frontend builder suites passed 33 tests with service/canvas mocks. These 110 backend and 33 frontend passes cover selected code paths, not full worker/provider acceptance.

Actual Python functions with in-memory stores and explicitly mocked DB/cache/events/enqueue/send boundaries reproduced DOC-CODE-087–097. The public worker entry returned prior_step_incomplete without dispatch for the synthetic pending loop-body case. Actual frontend helper/hook bodies were transformed with installed esbuild and executed with local React setter/callback stubs; all four loaded presets were then checked by the actual backend validator. No repository tests, application source, schemas, flags or dependencies were changed, and no message, live database operation or provider request occurred.

From repository root, the bounded core command is `PYTHONPATH=shared .venv/bin/python -m pytest -q shared/api/tests/test_companion_workflow_dag.py shared/api/tests/test_companion_workflow_dag_tool_adapter.py shared/api/tests/test_dag_tool_bindings.py shared/api/tests/test_companion_workflow_dag_loop_expression.py shared/api/tests/test_companion_workflow_dag_advanced_logic.py`. Frontend checks run from shared/web/frontend with `node node_modules/vitest/vitest.mjs run src/features/ewa/companionWorkflowDagBuilder/__tests__ --maxWorkers=1`. These commands assume the existing local runtimes; they do not install tools or enable live execution.

Earlier Phase/Sprint completion labels described implementation milestones, not today's production acceptance. Remaining engineering work includes the separate [append-only code log](../../../docs/CODE_ISSUES.md), public confirmation recovery, actual tool/provider contracts, queue/outbox/idempotency/OCC behavior, typed authoring/mirror parity, safe document/vision ownership and resource bounds, and real browser/worker integration. The [extension guide](EWA-COMPANION-CHAT-AND-WORKFLOW-EXTENSION-GUIDE.md), individual job/provider contracts and repository-wide audit queue retain their own review scope.
