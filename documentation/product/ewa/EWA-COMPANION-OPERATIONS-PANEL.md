# Companion operations panel and task-run transport

Product technical reference · source review dated 2026-10-11. This guide covers task-run delivery, client polling/SSE/store behavior and operation-card ownership. It records implemented source boundaries; it does not certify a deployed worker, completed generation, whole agentic mission or every embedded editor contract.

## Data ownership

The panel displays durable `ewa_companion_task_runs` and `ewa_companion_task_steps` from the EWA pool. [Persistence](../../../shared/api/ewa_platform/persistence_pg/companion_task_asyncpg.py) stores revisioned runs, workflow/version fields, a parent link, payloads and timestamps. Its row converter decodes JSON strings and returns ISO timestamp strings.

UGS `generation_requests` and EWRP `ewrp_jobs` belong to the main application database. They remain separate stores; the panel does not list their histories directly. Music/image/presentation jobs and agentic adapters mirror selected state/results into companion runs. A chat promise without a durable run is not evidence of dispatch. Not every synchronous tool or desktop action creates a run.

Useful producer entries are [media handlers](../../../shared/api/ewa_platform/companion/orchestration/tools/handlers_media.py), [music stage events](../../../shared/api/ewa_platform/companion/jobs/music_pipeline_progress.py), [image orchestration](../../../shared/api/ewa_platform/companion/orchestration/companion_image_generation.py) and [presentation orchestration](../../../shared/api/ewa_platform/companion/orchestration/companion_presentation_generation.py). Detailed generator gates, billing, provider deadlines and recovery belong to [music](EWA-COMPANION-MUSIC-GENERATION.md), [images](EWA-COMPANION-IMAGE-GENERATION.md) and [EWRP](../EWRP-REVOLUTIONARY-PRESENTATIONS.md); those linked guides are not accepted by this review.

Current presentation orchestration creates through `ewrp_create_service` and polls status through the main-database service. The older HTTP self-call/JWT-status-poll description is obsolete. [Music](../../../shared/api/ewa_platform/companion/jobs/music_run_reconcile.py), [image](../../../shared/api/ewa_platform/companion/jobs/image_run_reconcile.py), [presentation](../../../shared/api/ewa_platform/companion/jobs/presentation_run_reconcile.py) and [generic](../../../shared/api/ewa_platform/companion/jobs/generic_run_reconcile.py) recovery are separate mechanisms; no universal completion deadline follows from a card.

## Authenticated HTTP contract

All six routes below use `require_oauth2_user` in [companion_chat.py](../../../shared/api/ewa_platform/gateways/routers/companion_chat.py), mounted under `/api/v1/ewa`. Principal identity comes from the authenticated user's id. The source route path parameter is a string; the separate status tool's UUID parser is not this route's validator. Common authentication behavior is described in [HTTP reference](../../api/SOURCE-HTTP-REFERENCE.md).

- `GET /api/v1/ewa/companion-chat/task-runs`: `limit=10`, range 1–100; `include_steps=false`; `list_profile=summary`, literal `summary` or `full`. Returns `{"runs":[…]}`. The SQL selects top-level rows only, active statuses first, then descending update and creation times.
- `GET /api/v1/ewa/companion-chat/task-runs/{run_id}`: `include_steps=true` by default. Returns one typed run, with principal-scoped 404 for an absent/other-principal id.
- `GET /api/v1/ewa/companion-chat/task-events/stream`: principal-wide Redis lifecycle stream; no initial run list/snapshot and no EWA-pool check in this route.
- `GET /api/v1/ewa/companion-chat/task-runs/{run_id}/events`: verifies owner, emits a full `run_snapshot`, then subscribes to that run's principal channel filter.
- `POST /api/v1/ewa/companion-chat/task-runs/{run_id}/confirm`: JSON `decision` normalized to `confirm` or `cancel`, optional `expect_run_revision>=1`. Returns `ok`, `reply`, `actions` and typed `task_run`.
- `POST /api/v1/ewa/companion-chat/task-runs/{run_id}/cancel`: no request model/revision body. Returns `ok`, `reply`, typed `task_run` and `ugs_requests_cancelled`.

Except for the principal-wide stream, these routes require the EWA pool; absent pool returns 503 `ewa_orchestration_pool_unavailable`. Detail/scoped-stream/mutations return 404 `companion_task_run_not_found` for a missing scoped row. Invalid list/body constraints produce framework 422 before business handling.

The list GET with `include_steps=true` invokes [poll-time recovery](../../../shared/api/ewa_platform/companion/workflows/user/declarative_advance.py) before reading rows. It can advance a personal workflow from a completed child and calls stalled-image recovery, which can enqueue/start a job when its checks pass. This GET is not universally read-only. The image recovery currently rejects ISO timestamp strings returned by normal persistence, so its intended kick path is limited by DOC-CODE-051.

### Run and step fields

[Models](../../../shared/api/ewa_platform/schemas/pydantic/companion_chat.py) require run `id`, `principal_id`, `status`, `intent_kind`, `user_message`. Payload fields default to empty mappings: `plan_payload`, `confirmation_state`, `result_payload`, `error_payload`; `execution_mode` defaults to `sync`, `run_revision` to 1, `parent_run_id` to null, timestamps to null and `steps`/`surface_blocks` to empty lists. Status/execution mode are strings, not restricted enums in this output model. Persistence workflow id/version fields are not separate fields in the typed HTTP run; workflow identity can be in the full plan payload.

Steps require `id`, `run_id`, integer `step_index`, `step_kind`, `status`, `title`; input/output/error mappings default empty and timestamps nullable. `include_steps=false` does not synthesize a complete timeline. The raw [task-status tool](EWA-COMPANION-TASK-STATUS-TOOL.md) reads the same store but has its own result/error/progress shape and does not receive the HTTP delivery transformations.

### Summary and full delivery

[Summary shaping](../../../shared/api/ewa_platform/companion/orchestration/task_run_list_summary.py) filters four mappings using fixed allowlists, caps `plan_summary` at 480 characters plus ellipsis, and sets `surface_blocks=[]`. It leaves supplied step rows intact; summary with steps is not a total payload-size bound. `full` list/detail/scoped snapshot retain full run payloads and attach surface descriptors.

The summary preserves selected mission/gate/preview identifiers, but currently drops personal workflow id/title fields, content availability tombstones, `background_play`, presentation title/topic/PDF token and result progress. With normal timestamp merge, a summary row can replace a full row and lose that data. Personal workflow recognition/cancel and missing-content suppression can consequently differ between full and polled state. DOC-CODE-047 records actual trim/merge/helper probes; complete live UI frequency remains unverified. Do not assume all card-required fields survive summary mode.

The [content guard](../../../shared/api/ewa_platform/companion/operations/result_payload_content_guard.py) checks known UUID references in result and step-output mappings against non-deleted main-catalog rows. Missing references keep their ids and gain `{field}_status=missing`; primary references gain `unified_content_availability=missing`. A matching `/api/v1/content/{id}/download` image URL is cleared. It does not recursively inspect arbitrary payloads, change PG rows or verify remote URLs. No catalog pool/query failure returns the original mapping, without verified availability.

Current collection uses a field-name dictionary across steps and list rows. Repeated `unified_content_id` keys with different ids overwrite earlier values before lookup; an unchecked missing item can be marked available. DOC-CODE-044 reproduces this. Summary filtering can subsequently remove even correctly produced tombstones (DOC-CODE-047).

[Surface blocks](../../../shared/api/ewa_platform/companion/surface_blocks.py) derive one block per run: awaiting confirmation → `confirm`; any steps → `workflow_timeline`; terminal without steps → `result`; otherwise timeline. Existing nonempty blocks are retained. Confirm descriptors route both decisions through the existing Confirm endpoint and can supply a chat follow-up. Reserved/client-rendered `choice`, `builder`, `history_ref` and `text` kinds are not generated by this run shaper; a descriptor does not grant execution authority.

### Confirm and cancel outcomes

Normal Confirm requires status exactly `awaiting_confirmation`, otherwise 409 `companion_task_run_not_awaiting_confirmation`. With an explicit expected revision, reported mismatch returns 409 `companion_task_run_revision_conflict`. A missing result mapping returns 502 `companion_task_confirm_failed`. Agentic runs delegate to a separate confirmation service; unsuccessful outcomes return 409 with its reason. Returned steps are not loaded in the Confirm preparation path.

A successful HTTP envelope does not imply a successful operation: the normal route returns `ok=true` when its service supplies a failed run. Generic public workflow confirmation also has the state-loss defect recorded in DOC-CODE-036; inline/custom continuation limits are in [workflow registry](EWA-COMPANION-WORKFLOW-REGISTRY.md).

[Cancellation service](../../../shared/api/ewa_platform/companion/orchestration/task_run_cancel.py) accepts active `pending`/`running`/`awaiting_confirmation` music, image/edit-image, agentic and recognized personal action-workflow runs, excluding a confirmation claim in progress. Presentation and ordinary operator builtin action workflows are not accepted by this cancel predicate. Unsupported/current terminal states return route 409 `companion_task_run_not_cancellable`.

Music/image cancellation attempts correlated UGS requests. Personal-workflow cancellation visits up to 16 active children before the parent and clears cached worker auth; agentic cancellation also attempts the session transition/mirror. These calls are not one cross-store transaction. Main DB manager unavailability returns 503 `database_unavailable`; missing refreshed run returns 502 `companion_task_cancel_failed`. Final reply follows refreshed status; `ok` comes from the service and is not a count of completed cancellations. No physical/provider cancellation guarantee follows from `ugs_requests_cancelled` alone.

## Lifecycle SSE

[Redis bridge](../../../shared/api/ewa_platform/companion/jobs/task_events.py) uses one channel per principal and JSON envelopes with `event`/`data`. Publish is best effort; async publishing wraps the sync call in `asyncio.to_thread`. Redis is notification transport, not a durable task ledger. There are no SSE event ids, replay cursor, Last-Event-ID recovery or historical event log here.

Both task streams emit two-second keepalive comments while waiting. Redis iterator exit ends the route's pump; subscription failures are logged and can close the stream. The queues have no explicit max size. Run filtering uses `run_id`, `task_run_id`, `id` or nested `task_run.id`. The principal-wide stream has no run snapshot.

Scoped stream emits `run_snapshot` before subscribing. If the initial run is terminal, it sends `done {ok:true}` and closes. Otherwise `task_completed` or `task_failed` sends the same done marker and closes; the marker means stream termination, including failed/cancelled payloads, not successful execution. The route does not continuously poll PG. Plain Redis lifecycle messages are not re-sanitized by the HTTP content guard.

The [client](../../../shared/web/frontend/src/services/ewa/ewaCompanionChatTaskRunsApi.ts) uses authenticated fetch with session handling, not browser `EventSource` without Bearer. Full snapshots are coerced separately. [Stream hook](../../../shared/web/frontend/src/features/ewa/companionOperations/useCompanionTaskEventsStream.ts) selects scoped mode for one active displayed id, principal-wide mode otherwise. It buffers store updates, flushes on terminal observation, requests a list refresh and aborts a terminal scoped stream once. Ordinary successful EOF reconnect waits 5 seconds; error backoff starts at 3 seconds and caps at 30 seconds. Disable/unmount aborts the subscription. Event dispatch/transport completion is not a whole-job SLA.

## Polling and state merge

[Runtime](../../../shared/web/frontend/src/features/ewa/companionOperations/useCompanionOperationsRuntime.ts) is enabled when the EWA surface and browser tab are visible in [panel orchestration](../../../shared/web/frontend/src/features/ewa/companionUx/useCompanionChatOrchestrationBase.ts). It performs an immediate list fetch when enabled, using summary, cache bust and `includeSteps=true`; generic client list defaults are separate. Focus/visibility refresh is ignored while the document is hidden.

Fetch/display sizes in [display helpers](../../../shared/web/frontend/src/features/ewa/companionOperations/companionOperationsDisplayFilters.ts) are 12/8 initially, 25/20 after Show more, with a 30-run store cap. The old fixed ten-row UI history claim is obsolete. Children with a column or legacy plan parent link are hidden; nested agentic pending-run ids are also hidden. Active personal workflows dedupe by workflow id plus normalized message when identity survives the payload.

Polling intervals in source are 300 seconds for active runs when SSE is enabled, 20/45 seconds for active runs with SSE disabled, and 120 seconds for idle foreground. Idle non-foreground stops scheduling after its fetch. The runtime derives SSE enabled from `pollEnabled && hasActiveOperations`, without connected/healthy feedback from the stream hook. An active run can therefore remain on five-minute safety polling during SSE failure; the documented 20/45-second outage fallback is not implemented (DOC-CODE-048). Foreground means desktop window active; the visible-surface gate is a separate input.

[Zustand store](../../../shared/web/frontend/src/features/ewa/companionOperations/companionOperationsStore.ts) owns poll/SSE/chat patches. Runtime callbacks live in an imperative bridge and parent callback refs. Derived transcript selectors cache by run reference and other relevant inputs. Notify suppression compares payloads, steps, blocks and timestamps as well as id/status/revision; it is not only an id/status/revision check.

Poll merge is a timestamp-selected union, capped to 30, with special preservation of client music substages. It does not replace the entire list or remove every absent row. Incoming equal/newer timestamps replace the row as a whole, which permits summary field loss. Manual refresh has a generation guard against an older manual response; periodic poll uses its own alive flag and is not the same global request sequence.

Confirm sends the stored run revision, patches the returned run, dispatches returned allowlisted actions and refreshes. Current Confirm Zod parsing strips task_run down to id; coercion supplies pending/unknown/empty payloads and revision 1 (DOC-CODE-046), so the immediate snapshot is unreliable. Cancel coerces its response without that Confirm schema, then patches/refreshes. Neither runtime handler interprets `ok=false` as a thrown HTTP error by itself.

[Display-state helper](../../../shared/web/frontend/src/features/ewa/companionOperations/companionOperationsMissionSurface.ts) demotes running/pending/replanning state to stale when the timestamp is absent or older than five minutes; this applies to non-agentic operations too. Poll failure can also demote live-looking state. Status chips normalize aliases such as queued, processing and succeeded; unknown statuses fall back to pending. An active-id selector or enabled SSE flag is not proof of a fresh heartbeat.

## Card ownership and local controls

[Desktop panel](../../../shared/web/frontend/src/features/ewa/companionOperations/CompanionOperationsPanel.tsx) owns expansion/refresh chrome and metrics, then delegates to [UniversalOutputSurface](../../../shared/web/frontend/src/features/ewa/companionOutputSurface/UniversalOutputSurface.tsx). Viewport mode uses measured height with a minimum/fallback. Desktop right rail passes secondary mode; [mobile sheet](../../../shared/web/frontend/src/features/ewa/companionUx/CompanionMobileOperationsSheet.tsx) keeps primary confirm/cancel/media controls and scrolls to a focused run. Browser/device/accessibility acceptance has not been executed.

[Local lifecycle](../../../shared/web/frontend/src/features/ewa/companionOutputSurface/companionSurfaceLifecycle.ts) stores pin/dismiss/restore and mission collapse preferences in `eliteew.ewa.surfaceLifecycle.v1.<principalId>`. It is view state, not the task ledger. Close does not cancel. Terminal cards currently remain in the active surface zone until closed, or in pinned when pinned; status/history counters and surface zones are different concepts. The old automatic terminal-card history-zone claim is obsolete. Dismiss/collapse collections cap at 80 and storage failures fall back without a persistence guarantee.

[Center mission](../../../shared/web/frontend/src/features/ewa/companionUx/CompanionCenterMissionCanvas.tsx) uses a desktop two-column answer/execution layout for an active agentic mission with details, while smaller layouts stack. Tree/trace panels have a four-second poll for nonterminal session status. Terminal chrome defaults collapsed unless locally expanded; active chrome ignores collapse. These presentation rules do not accept agentic lease, child recovery, checkpoint or gate behavior as a whole.

[Run card](../../../shared/web/frontend/src/features/ewa/companionOperations/CompanionOperationRunCard.tsx) derives track/image/presentation affordances from [ready-artifact helpers](../../../shared/web/frontend/src/features/ewa/companionOperations/progressUi/readyArtifacts.ts). Known missing content suppresses media readiness; completed status alone is insufficient for track/image actions. Image previews fetch authenticated blobs. Presentation controls prefer a token-bearing direct URL when available, otherwise authenticated PDF blob download; direct-token behavior is not always a fallback. Main PDF/editor/billing ACLs remain product-owned.

Retry currently selects a localized generic prompt from [an intent allowlist](../../../shared/web/frontend/src/features/ewa/companionOperations/companionRetryPrompts.ts), not the original saved generation prompt. It allows music/image/presentation and `user_action_workflow`; ordinary `action_workflow` is not that key. A retry request starts normal routing and is not a guaranteed same-run revision/replay. Music progress has the pending-stage issue in DOC-CODE-042, now also reproduced in the frontend helper.

## Embedded output surfaces

File list and document editor are separate output-surface modes sharing the companion window; they are not task-run result serialization. [File list](../../../shared/web/frontend/src/features/ewa/companionOutputSurface/CompanionFileListMode.tsx) opens a selected item in document_editor mode and politely announces an empty list. The click changes local mode; document loading/saving is separate.

[Editor hook](../../../shared/web/frontend/src/features/ewa/companionOutputSurface/companionDocumentEditor/useCompanionDocumentEditorMode.ts) uses a selected-text or document context for AI transformation, offers a candidate and checks pre-insert permission before applying it. This is a UI boundary, not full DocEditor/content ACL acceptance. [Document client](../../../shared/web/frontend/src/services/ewa/ewaCompanionDocumentSurfaceApi.ts) normally saves through content replace-file, falling back to DocEditor PUT; force save uses the PUT path. Only the PUT branch carries expected_version. The primary replace path omits the known version and the backend route does not pass one to storage (DOC-CODE-050). Do not claim every save is revision-checked. Draft/autosave/collaboration/structure contracts require their dedicated review.

UGS tray/stuck-task notifications, billing history and embedded workflow builders have separate ownership. See [desktop UGS](../desktop/UGS-DESKTOP-SHELL.md), [user UX](EWA-COMPANION-USER-UX-MAP.md) and [personal workflows](EWA-COMPANION-USER-WORKFLOWS.md). Current topology and host/container identities belong only to [production topology](../../platform/PRODUCTION-TOPOLOGY-STATE.md#current-2026-07-30--living); this guide does not repeat a deployment inventory.

## Verification and remaining acceptance

Existing summary/surface/revision/parent-link/task-event backend selection: **29 passed, one module skipped** because `jose` is unavailable. The skipped orphan-content module, including its synchronous HTTP test, is not accepted. Nine frontend store/runtime/stream/buffer/mode/partition/panel/lifecycle suites: **37 passed, 2 failed**. Both failures expect live/active display for fixtures without a heartbeat timestamp; source correctly classifies them stale, so these assertions require reviewed fixture/expectation repair (DOC-CODE-049).

Isolated async ASGI also verified summary/full/detail 200, missing-run 404, list/body 422, unsupported cancel 409, pool/main-DB 503, failed-run Confirm with ok=true, terminal snapshot/done and principal stream without a snapshot. Dependencies/event delivery were mocked and no application lifespan was started; this is route-boundary evidence, not storage/auth-provider integration.

Ephemeral probes used actual pure functions or mocked persistence/API dependencies. They reproduced content-id overwrite, active_count undercount, Confirm field stripping/coercion, summary field loss, frontend pending progress, version omission and image recovery timestamp mismatch. Node's TypeScript stripping emitted an experimental API warning. No application/test fix, real SQL, content write, worker enqueue, Redis call, provider request or deployment was executed.

For an authorized future environment acceptance: compare summary/full/detail responses; observe owner isolation and 404/409/503/422 paths; exercise explicit gate decisions and revision conflicts; disconnect/reconnect both stream modes; verify missed-event recovery and stale display; generate/cancel supported media with correlation; test pin/close/restore, mobile focus and accessible failure states. These are pending checks, not passed smoke results or a promised 1–3 minute generation time.
