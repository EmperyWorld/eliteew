# EWA companion personal workflows

Reference · source contract reviewed 2026-10-11. Personal workflows are principal-owned phrase-triggered definitions with CRUD, validation and a companion output surface. This guide owns personal persistence, HTTP, matching and linear v1 execution, plus the v2 save/validation boundary. [Workflow registry](EWA-COMPANION-WORKFLOW-REGISTRY.md) owns operator catalog and builtin actions; [DAG engine](EWA-COMPANION-WORKFLOW-ENGINE-V2.md) retains separate graph/worker/visual-builder review scope. Personal workflows, product plans and [multi-intent queues](EWA-COMPANION-MULTI-TASK-ORCHESTRATION.md) are different contracts. No live database, Redis, broker, provider or deployment acceptance is implied.

## Ownership and persistence

[Persistence](../../../shared/api/ewa_platform/persistence_pg/companion_user_workflows_asyncpg.py) and [migration 015](../../../shared/api/ewa_platform/migrations/applied/015_ewa_companion_user_workflows.sql) define ewa_companion_user_workflows. The UUID id is independent of workflow_id inside definition_json. principal_id is a UUID scoping column; this DDL declares no user foreign key. Every CRUD query supplies the authenticated principal, and name uniqueness is case-insensitive per principal through lower(name). Stored name length is 1–120 characters.

Rows contain name, enabled, definition_json, trigger_json, integer version and created_at/updated_at. The adapter JSON-decodes string JSONB values and shapes UUID/time fields as strings; it does not assume a driver-wide JSON codec. Row version starts at 1 and increments on nonempty updates. No expected-version parameter or compare-and-swap protects concurrent edits. V1 definition rebuild starts version at 1; v2 graph PATCH increments definition version, while metadata-only PATCH preserves it. Row version and definition version are not interchangeable.

List returns all principal rows ordered by updated_at descending then name, without pagination. Trigger matching/collision analysis requests only the most recent 32 enabled rows (adapter permits 1–64). Saving an enabled row below that selection does not guarantee it will be considered on the next turn. DELETE removes the definition row; it is not task cancellation or a transactional purge of already running parents/children.

## Authentication, routes and response contract

[HTTP router](../../../shared/api/ewa_platform/gateways/routers/companion_user_workflows.py) is mounted at /api/v1/ewa/companion-user-workflows. Every declared route depends on require_oauth2_user and takes principal_id from auth_user.id. These are OAuth-authorized user endpoints; a companion session id alone is not their credential. Public shapes are [Pydantic models](../../../shared/api/ewa_platform/schemas/pydantic/companion_user_workflow.py); the [client](../../../shared/web/frontend/src/services/ewa/companionUserWorkflowsApi.ts) uses /ewa/... with shared baseURL /api/v1, generated OpenAPI type aliases and skipAuthRedirect=false.

- GET /tool-catalog returns the typed catalog list, including bilingual labels/descriptions, async_step, requires_confirm and input fields/options. It requires the personal-workflow feature but no orchestration pool.
- POST /validate accepts name, trigger, steps and optional exclude_workflow_id. It constructs a v1 create payload and returns ok/errors/warnings, execution_mode and preview_steps. With a pool it adds enabled-row phrase collision warnings; without a pool it performs pure analysis. This route validates and previews; it does not run tools.
- POST /validate-v2 accepts a complete v2 definition and returns graph/quota validation, including max_nodes_allowed, counts, ordered/entrypoint ids, errors and warnings. It uses auth_user.is_verified and does not require a pool or enabled v2 execution.
- GET collection returns a row list. POST collection accepts name/enabled/trigger and exactly one of steps or dag, builds and persists a definition, and returns the row with HTTP 200.
- GET /{workflow_id} returns one principal row; PATCH supports name/enabled/trigger and either replacement steps or a dag body. DELETE returns {"deleted": true}. Missing principal rows return 404 user_workflow_not_found.
- POST /{workflow_id}/enable and /disable update the outer row's enabled flag and return the row. They do not synchronize definition.enabled; an initially disabled definition can remain unmatchable after enable (DOC-CODE-077).
- GET/PATCH /observation-triggers declare idle_enabled/focus_app_enabled/persisted and optional boolean patches. They are registered after the dynamic GET/PATCH /{workflow_id} routes, which currently capture that literal path. DOC-CODE-076 records actual ASGI selection of the dynamic routes; declared schemas do not establish a working preference endpoint.

CRUD requires an EWA orchestration pool and returns the shared 503 pool-unavailable error when absent. Most routes call the personal-feature check and return 503 companion_user_workflows_disabled; the declared observation handlers omit that feature check, although their shadowing dynamic handlers apply it. Model-invalid bodies normally produce 422; domain validation errors return 422 with detail.errors. UUID path variables are plain strings before SQL UUID casts. Duplicate-name driver exceptions are not translated into a stable 409, and empty steps PATCH currently raises uncaught validation and yields 500 (DOC-CODE-079). Do not promise every invalid request returns 422.

## Authoring and validation

[Authoring models](../../../shared/api/ewa_platform/companion/workflows/user/user_workflow_validation.py) allow a 1–120 character name, enabled=true by default, and 1–8 nonempty stripped phrase patterns of at most 200 characters. The trigger type field is a string rather than a strict phrase enum. Generated matching uses escaped case-insensitive word-boundary regexes, so patterns are literal phrase material rather than arbitrary supplied regular expressions. Punctuation/emoji edges can fail to match the identical phrase (DOC-CODE-086).

Linear creation allows 1–6 steps. Each is a tool or explicit confirm_gate, with optional titles and args_template. Confirm gates have empty args. Tool names must be in the server's 31-tool allowlist. [Allowlist and catalog](../../../shared/api/ewa_platform/companion/workflows/user/user_workflow_allowlist.py) owns the complete names, accepted field keys, required/recommended fields and metadata. The catalog currently covers all 31 allowed names; that does not certify runtime authorization, readiness or complete tool result schemas.

Argument sanitization drops unknown keys, None and empty strings, and trims accepted strings; nonstring accepted values remain. Private auto-accept keys are absent from this v1 public key list. Builders add authoritative turn.user_line to templates, and dispatch again supplies the actual line. Required fields reject missing/empty strings; placeholders count as filled even if they later resolve to empty. Recommended fields produce warnings. Tool-local authorization, input and confirmation checks still apply after authoring validation.

Analysis warns about duplicate/short/vague phrases, collisions, multiple async steps, sync after async, confirmation-required tool before the final step and missing recommended fields. Collision detection compares exact lowercase phrase strings among the bounded enabled-row selection; it is not regex-overlap analysis or a save lock. V1 create validates payload but does not persist a collision analysis result. Warnings are advisory.

Generated v1 execution_mode is async for music_generation, music_generation_xl_base, image_generation or presentation_generation, otherwise sync. Eight tool names receive requires_confirm metadata: file_create, file_save_text, file_delete, file_rename, file_rewrite, operation_cancel, telegram_sender and email_dispatcher. That metadata is not a universal injected gate: the linear dispatcher handles explicit confirm_gate and handler status needs_confirm. In particular, immediate rewrite behavior must be assessed under [file tools](EWA-COMPANION-FILE-CATALOG.md). Do not label this entire allowlist universally safe or automatically confirmed.

V2 authoring uses nodes/edges, optional builder_meta and execution_mode (async default), with a schema cap of ten nodes. /validate-v2 applies tier limits of 3 regular / 10 verified. The pooled CRUD collision helper hardcodes unverified context, so even a verified user's four-node graph can validate successfully then fail save with max 3 (DOC-CODE-080). Persisting a DAG is independent of enabling its runtime; full node, edge, binding, expression, branching, loop and worker behavior belongs to the DAG guide's separate review.

## Matching and version semantics

[Matcher](../../../shared/api/ewa_platform/companion/workflows/user/user_workflow_triggers.py) requires the personal feature and a nonempty line, loads enabled rows, parses each definition and checks definition.enabled. It searches definition.triggers and selects the first regex match in persistence order. trigger_json is used by the list/collision UI, not by execution. A v1 trigger-only PATCH updates trigger_json without rebuilding definition.triggers: the visible new phrase can fail while the old phrase still runs (DOC-CODE-078). V2 metadata PATCH regenerates its definition's triggers/enabled/titles; v1 metadata and toggle paths have different behavior.

[Action starter](../../../shared/api/ewa_platform/companion/workflows/action/starter.py) tries a personal match before operator/catalog matching. V1 goes to the generic declarative starter; v2 requires the engine-v2 gate and routes to the separate DAG starter. This describes action-starter precedence, not precedence over every earlier chat/quick/pre-tool branch. [Multi-intent routing](EWA-COMPANION-MULTI-TASK-ORCHESTRATION.md) owns the full turn ordering.

The v1 resume loader fetches the current personal row by user_workflow_id; it does not select a definition snapshot matching the run's recorded workflow_version. Editing/deleting a definition during an active run can change/remove its remaining execution definition (DOC-CODE-082). Disabling future matching is not cancellation of an existing run. No immutable execution or complete replay guarantee is established by the version columns.

## Linear v1 execution and result limits

[Starter](../../../shared/api/ewa_platform/companion/workflows/user/generic_workflow_starter.py) creates an action_workflow parent with workflow id/version, personal row id and titles, then persists every step and dispatches step 1. A retrigger can reuse an active matching personal parent among only twelve recent task rows; this is a lookup rather than an atomic deduplication claim. The starter returns the first tool's reply/actions and its task row or the originally created parent. A first-step gate/failure may therefore need a later task read to expose updated parent status.

[Template context](../../../shared/api/ewa_platform/companion/workflows/action/context.py) supports turn.user_line/principal_id, steps.<zero-based index>.input/output and steps.by_key.<key> paths, recursively within strings/dicts/lists. Unknown paths become an empty string; string interpolation stringifies values rather than preserving structured output types. Dispatch supplies router bypass and [parent/step arguments](../../../shared/api/ewa_platform/companion/workflows/user/workflow_parent_link.py); bypass skips selected line intent predicates, not tool authorization or every feature gate.

[Linear dispatcher/advance](../../../shared/api/ewa_platform/companion/workflows/user/declarative_advance.py) distinguishes explicit confirmation, synchronous ok/memory_append, accepted/background and failure/unhandled responses. It marks step rows and advances synchronous chains or linked child completions. An explicit confirm gate writes parent awaiting_confirmation with step_key; public custom continuation/gate-state limitations already recorded in DOC-CODE-036–038 still apply. Confirm controls in the UI do not establish successful resume.

The starter advances a synchronous success only when there is more than one step. A one-step success can leave its completed step under a running parent (DOC-CODE-081). For multistep sync chains, dispatch first stores reply/status/tool plus data, then advance can replace that output with nonempty raw data; subsequent reply templates become empty. Later inline actions/replies are not accumulated into the starter's first response (DOC-CODE-083). Do not promise complete per-step review or delivery of every client effect.

Linked asynchronous child completion can advance a parent. Legacy orphan repair uses intent/tool, principal and exact user_message against a bounded recent active-parent selection; it is heuristic, not global exactly-once execution. Poll reconciliation scans bounded parents/children and can trigger recovery work, including image kicks. Completed parent/step guards exist, but no full concurrent/transactional/worker restart acceptance was performed. [Operations](EWA-COMPANION-OPERATIONS-PANEL.md) owns list/detail/SSE/Confirm/Cancel and parent/child display.

## OAuth snapshot and feature boundaries

[Auth cache](../../../shared/api/ewa_platform/companion/workflows/user/workflow_auth_cache.py) stores bearer token, OAuth user id and optional profile in a Redis snapshot keyed by parent run id, separately from plan_payload. Default TTL is six hours with a sixty-second minimum. The synchronous Redis client uses one-second connect/read timeouts and a selected Celery Redis database; storage is best effort and disconnects the pool. Missing/expired/invalid snapshots yield a base background ToolContext without restored bearer/auth_user/profile. That can prevent authenticated tools from advancing; it is not transparent durable authentication.

Successful terminal advance schedules snapshot deletion through asyncio.to_thread. This source does not establish deletion on every failure/cancellation path or live Redis expiry. Never dump the snapshot or bearer into debugging examples. Logs expose cache stored/skip/miss/failure and workflow dispatch/advance/reconcile markers, not proof of successful external work.

[Feature helpers](../../../shared/api/ewa_platform/companion/workflows/config.py) give USER_WORKFLOWS_ENABLED an independent fallback of 1. Linear CRUD/matching is not universally gated by the operator WF_ENGINE switch. DAG engine-v2 requires WF_ENGINE, DAG_CELERY_ORCHESTRATION_ENABLED and WORKFLOW_ENGINE_V2_ENABLED; outbound send and tool-registry adapter have separate helpers. Helper, settings-catalog and seeded values can differ: use [settings](EWA-PLATFORM-SETTINGS-DB.md) for precedence. Addresses, hosts, models and current placement belong only to [topology §Current](../../platform/PRODUCTION-TOPOLOGY-STATE.md#current-2026-07-30--living).

## Client surfaces and observation preferences

[Surface intent helper](../../../shared/api/ewa_platform/companion/workflows/user/user_workflow_builder.py) recognizes builder/edit/roadmap phrases in that order and returns workflow_dag_builder, workflow_edit or roadmap without creating a definition or running tools. Examples include “create workflow” / “создай цепочку”, “my workflows” / “мои цепочки” and plan-view phrases. Surface display is not a saved/running automation.

[List UI](../../../shared/web/frontend/src/features/ewa/companionOutputSurface/CompanionWorkflowEditMode.tsx) loads rows and the catalog, merges a just-saved optimistic row if absent, filters all/enabled/disabled and exposes toggle/delete. DAG rows offer visual edit/duplicate; legacy linear rows remain listed with a read-only badge and no edit/duplicate action. New creation opens the DAG builder. Failure reload can present only the optimistic row or an empty list; it is not proof the server has no workflows. Action failures reload and show an inline alert, with a special already-gone 404 notice.

[Catalog fallback](../../../shared/web/frontend/src/services/ewa/companionUserWorkflowToolCatalogFallback.ts) normalizes local metadata, seeds every fallback entry, then overlays server entries; empty server fields retain fallback fields. It does not remove local tools absent from the returned server catalog. This supports authoring during outages but cannot confer server allowlist/feature permission. Starter templates and local step helpers are authoring inputs, not executed acceptance fixtures; their parameters/placeholders still require validation and compatible results.

[Observation mirror](../../../shared/web/frontend/src/features/ewa/companionObservationTriggerPrefs.ts) caches idle/focus booleans under eliteew.companion.observationTriggers.v1:<principal>, defaults both true, and falls back to local values after server failures. Save writes local state first and returns it on failed PATCH. [Settings panel](../../../shared/web/frontend/src/features/ewa/companionOutputSurface/CompanionWorkflowObservationSettings.tsx) uses a load stall guard and optimistic toggles; local success does not certify server synchronization. The backend's declared preference helpers store a learned_preferences namespace on an existing profile and report persisted=false when absent. These controls govern observation submission, not phrase-triggered personal workflows or an independent server scheduler.
